# Geometry revisions of existing authored weapons

The Forge Custom create / original equipment study panel now has **Revise an existing custom weapon**. Load an existing item/display pair, choose a replacement GLB or stage the selected authored candidate, preview it with the registered texture, then apply the reviewed revision. This updates the existing custom registry model; it reserves no IDs and does not write `item_template`.

The supported contract is deliberately bounded: `glb_import`, one model → one display → one item, rigid bone-zero geometry, opaque single-sided single-pass material, one DBC texture, no private effect textures, particle/ribbon emitters or collision geometry. The importer rejects animations, skins and morphs. The existing source may have donor scaffold animation tables; those remain byte-for-byte intact. GLB import is `reorient=false`, with no decimation or shape controls. The replacement uses existing UVs/registered texture; embedded GLB texture pixels are ignored. Uploads are limited to 16 MiB and geometry to the existing 4,000-triangle Forge ceiling, which is a tooling limit rather than a claimed historical art budget.

## API

- `GET /WeaponForge/RevisionTarget?displayId=76338&itemEntry=1102495` returns current compiled model and texture SHA-256, name/family, build identity and MPQ member paths. It verifies the exact item/display registry pair, actual registry byte hashes, sharing/effect restrictions and live item/display/family binding.
- `POST /WeaponForge/ReviseGlb` uses multipart fields `file`, `displayId`, `itemEntry`, `expectedModelSha256`, `apply=false`. It imports and validates the source, compiles against the current stored M2 scaffold, independently validates emitted M2 bytes, verifies the preserved prefix, and returns `modelSha256`, `previousModelSha256`, `sourceSha256`, `textureSha256`, `revisionToken`, `qualityAudit` and the compiled `preview.glbWebPath`. Only preview cache artifacts are written; registry and gameplay are unchanged.
- To apply, send the identical file and IDs with `apply=true`, the original `expectedModelSha256`, plus `expectedRevisionModelSha256` and `expectedRevisionToken` from the dry run. The token binds the original texture/display/gameplay/source metadata and exact replacement bytes. The service repeats compilation, checks those values, locks/re-reads the registry in a transaction and compares all preserved state before a guarded model update. Stale state fails closed.
- `GET /WeaponForge/RevisionModel?displayId=...&itemEntry=...&expectedModelSha256=...` downloads the **current registry** M2 only if its byte hash matches the requested hash. It returns conflict on later changes rather than silently serving another revision.
- Applied responses include `receiptUrl` for `/WeaponForge/RevisionReceipt?revisionToken=...`. The durable JSON receipt lives under `App_Data/weapon-revisions`; the response itself is also downloadable from the panel. Original `DownloadBuild` artifacts remain historical and are not rewritten as though the initial build had used the revised geometry.

The only changed registry fields are compiled model bytes/hash, source GLB bytes/hash, writer version and validation state. Model/display/item/build identity, member paths, texture bytes, icon, item visual, DBC fields and gameplay JSON remain intact. Independent byte comparison permits changes in the preserved M2 prefix only to vertex/view header pointers/counts (`0x44..0x53`) and vertex bounds (`0xB4..0xCF`). New geometry and four equivalent views are appended; existing attachment positions remain intact and require renewed fit review if the silhouette changes.

After committing, the model member cache is invalidated, the audit entry is attempted, and the normal unified patch rebuild is queued. No rebuild, deployment, deletion, item recreation or gameplay reload occurs. `runtimeVerified` remains false. Audit/receipt failures after a successful registry commit are returned as warnings alongside the applied hashes rather than reported as an unapplied revision. A queue failure similarly returns the committed state and queue message; use the normal rebuild action after resolving it, rather than blindly reapplying stale source hashes.
